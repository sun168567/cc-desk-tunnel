# 远程操作执行端：三条线路的评估

2026-10-14 评估，起因是 [#70](https://github.com/sun168567/cc-desk-tunnel/pull/70)（桌面客户端开放 Web 工作台）。它提出的问题比这一个合并请求更大：人不在执行端跟前时，怎样继续驱动它上面的会话。本文记录对需求与场景的理解、三条线路各自的判断和理由，以及先后顺序。

方法：读了 #70 的全部代码，对照主线的多设备实现（服务端的设备归属检查、运行与执行通道的绑定、客户端的“其他设备”界面）。**三条线路都没有实现和实测**，改动量是读代码后的估计。

## 需求与场景

本项目把 agent 的运行端与项目的执行端分开：Claude Code 在 A（服务器）上运行，项目、工具链和命令执行在 B（开发机）上，B 上的客户端同时是操作界面。于是“操作 B 上的会话”默认要求人在 B 跟前，或者远程桌面到 B。

需求是：人在别处（设备 C）时，继续驱动 B 上的会话，例如看进度、点审批、补一句话、开一个新会话。按常见程度：

| 场景 | 人手上的设备 | 常见程度 |
| --- | --- | --- |
| 办公室的 B 开着长任务，回家用笔记本接着问 | 另一台装了客户端的电脑 | 高：多台电脑的开发者正是本项目的主要使用者 |
| 离开座位时看进度、点审批 | 手机或平板 | 中：多为轻操作 |
| 借用一台没装客户端的电脑 | 任意浏览器 | 低 |

现状的缺口：C 的客户端能在“其他设备”里看到 B 的会话，但只能“在本机继续”（接管到 C，要求 C 上有这个项目目录）或“分叉到本机”，不能让会话留在 B 上、由 C 驱动。

## 总的取向

三条线路互补而不是互斥：线路 1 解决“另一台装了客户端的电脑”，线路 2 解决“任意浏览器”，线路 3 把执行端从“有人用的桌面”推广到“无人值守的机器”。它们共享同一个前提：会话归属于项目所在的设备，运行用那台设备的执行通道；变化的只是**谁可以对它下指令、从哪里下**。

归属模型保持不变（见[复查记录](review-2026-10.md)第 1 条）：需要 CLI 持续工作的东西归设备，随连接存在的交互流归连接。三条线路都不改变这条规则。

## 线路 1：经服务端从另一台客户端驱动

**判断：做，优先级最高；欢迎合作实现。**

C 的客户端在“其他设备”里直接对 B 的会话发消息、审批、停止，也可以在 B 的项目下新建会话；运行仍在 B 上执行。

现在卡住它的只有“下指令的必须是会话所在的设备”这一条规则，执行层已经是按设备的：

| 环节 | 现状 | 需要的改动 |
| --- | --- | --- |
| 发消息、继续、压缩 | 发送者必须是会话所在的设备 | 允许同一使用者的任一设备 |
| 运行用哪条执行通道 | 运行记下发送者的设备，并检查发送者的通道就绪 | 改为会话所在的设备，检查那台设备是否在线 |
| 审批、停止、结束后台任务 | 只有运行所在的设备 | 同一使用者的任一设备，先到先得 |
| 原生终端 | 只在会话所在的设备 | 不变：终端是本机交互 |
| 新建会话 | 只能为自己建 | 可选的目标设备，项目从那台设备已知的项目里选 |
| 设备在线状态 | 协议里没有 | 服务端按执行通道是否就绪下发；“其他设备”里区分在线与离线，离线时不能发送并说明原因 |

估计规模：服务端约 50–100 行，客户端约 200–300 行，各加测试。新建会话的目标设备和在线状态要扩充协议、提升协议版本，宜与其他协议改动攒在同一版发布。

边界情况沿用已有机制：B 离线时运行按现有的宽限期等待；B 与 C 同时向一个会话发消息，按“运行中追加输入”处理；审批在两端都显示。

收益与代价：

- **不新增网络入口**，鉴权仍是现有的服务凭据。服务凭据代表使用者本人，本来就应按最高权限保管，这条线路不改变这一点。
- **会话不换设备**，系统提示词不变，提示缓存不受影响；接管则要告诉模型换了电脑。
- **外网可用**：C 连的是 A，A 本来就有公网入口。
- 局限：C 必须装客户端，覆盖不了手机。

## 线路 2：客户端开放 Web 端口

**判断：认可方向，作为依托于客户端的实验性功能；希望实现完备之后再合入，否则先缓一缓。**

客户端增加一项可选功能：开放一个 Web 端口，带独立的鉴权；能访问到这个端口并通过鉴权的设备，在浏览器里得到一套与客户端等效的操作界面。它可以看作 Windows、macOS、Linux 之外的又一个端，但不独立存在：前端复用同一份代码与构建，本机能力经客户端转接，执行仍走客户端已有的连接。

**范围上不负责网络可达性**：只保证本机与局域网能用；从其他网络访问需要使用者自己的组网，防火墙也由使用者处理。这让这一端保持小而清楚，不引入中继服务。

#70 已经基本按这个形态实现（约 3000 行，主进程约 1600 行，前端约 1300 行）。合入前希望收敛到以下几点：

| 方面 | 希望的做法 |
| --- | --- |
| 开关与监听 | 默认关闭；默认只监听本机；局域网访问单独打开，并提示明文传输只适合可信网络 |
| 鉴权 | 采用成熟的 Web 做法：随机配对码或使用者设置的足够长的密码，HttpOnly Cookie，只存哈希，登录失败限速；浏览器登录有有效期（例如 30 天无活动失效），客户端里可一键撤销全部 |
| 开放的操作 | 白名单逐项说明理由；删除类、改定时任务这类写操作重新确认是否需要 |
| 测试 | 鉴权、来源校验、限速、白名单和浏览器端的关键流程要有进仓库的自动测试 |
| 文档 | 写明不负责网络可达性与防火墙；写明配对码或密码等于这台电脑的控制权 |

持续成本要预先认清：以后每一项需要本机能力的新功能，都要决定网页端是否开放、怎样适配。这是客户端从“纯客户端”变成“同时也是服务端”的代价，所以要求它在合入时就足够完备，而不是合入后再补。

## 线路 3：无头 Linux 执行端

**判断：作为后续方向记录；在线路 1 之后做。**

一个没有图形界面的 Linux 客户端，只承担执行端：登录服务端，提供执行通道，以设备身份在线。它本身没有操作界面，由线路 1（其他客户端经服务端操作）或线路 2（它自己开放 Web 端口）驱动。这样三台机器各司其职：

```text
A：运行 Claude Code 的服务器
B：无头 Linux 执行端（项目、工具链、命令执行，常开）
C：人手上的客户端或浏览器
```

这与几家模型厂商正在推的“云端常驻的 agent 电脑”是同一个理念：agent 在一台常开的机器上长时间工作，人只在需要时从任意设备看一眼、给一句指示。本项目的差别在于三者都由使用者自己掌控，Claude Code 保持官方原样。

现成的基础比预想的多：

- macOS 与 Linux 客户端的执行端已经是独立模块（进程内 SSH 服务、登录 shell 环境采集、进程组回收），并在单独的 Node 子进程里运行，不依赖图形界面。
- 连接、重连、执行通道都在主进程的连接桥里，与界面分离。
- 断线后运行在服务端继续、设备连回来后接上，正适合常开的机器。

要新做的：

- 一个命令行入口与配置文件（服务地址、证书指纹、设备名、允许的项目目录）。
- 凭据保存：没有系统钥匙串时用权限受限的文件。
- 作为系统服务运行（systemd 单元），建议以专用用户运行，并说明 Claude 拥有这个用户的全部 shell 权限，必要时放进容器。
- 打包：不带 Electron 的独立包。

依赖关系：没有线路 1，无头执行端无从操作；所以它排在线路 1 之后。线路 2 若合入，也可以给它一个本地的网页入口，但不是必须。

## 先后与分工

| 顺序 | 事项 | 由谁 |
| --- | --- | --- |
| 1 | 线路 1：放宽下指令的设备限制、在线状态、为其他设备新建会话 | 维护者主导，欢迎合作 |
| 2 | 线路 2：#70 按上表收敛后合入 | #70 作者 |
| 3 | 线路 3：无头 Linux 执行端 | 线路 1 落地后再定 |

## 未验证

- 线路 1 的改动量只是估计；B 离线、宽限期内 C 继续发送、两端同时审批的实际表现。
- 线路 2 在不同浏览器、移动端上的可用性；局域网模式下的实际风险。
- 线路 3 的执行端模块脱离 Electron 运行时的依赖；登录 shell 环境采集在无桌面会话的机器上的表现。
