# 服务端 Web 客户端：方案与约定

这份文档记录 #70、#101 之后我们对 Web 客户端的讨论结论，作为后续实现和评审的依据，也供参与开发的贡献者对齐。它取代了此前这里记录的“远程操作的三条线路”：其中线路 1（在“其他设备”里操作别的电脑上的会话）已由 #90 实现，线路 2 演变为下文的方案，线路 3（无头 Linux 客户端）仍是后续方向；原文见本文件的 git 历史。

## 从 #70 到 #101

#70 在桌面客户端里托管一个 Web 服务，浏览器经桌面转发到服务端。评审时我们认为这等于在桌面里又造了一个服务端，建议改由服务端直接提供 Web 客户端：#90 之后服务端已经是多客户端中枢，任何在线设备都能操作别的设备的会话，浏览器只是又一个操作入口。

#101 按这个方向重做，结构上是对的：浏览器直连服务端，复用现有页面和协议，服务端用命令白名单限制浏览器能做的事。但它在此之上叠加了大量不必要的设计，见文末“对 #101 的评估”。下面的方案以主线为基础，复用当前项目的结构和代码，不沿用 #101 中多余的部分。

## 原则

- **Web 是纯新增功能。** 不管开不开 Web，已有功能都不受影响。可以共用代码，可以在共用的结构里加分支，但现有的功能闭环和回归测试必须保持原样。
- **只为存在的东西写代码。** 不为从未发布过的版本写兼容兜底，不为假想的并发路径加锁和恢复逻辑。多余的兼容会在项目里不断累积本不该存在的上下文，让后续的人和 AI 都跟着它走偏。
- **一个 PR 做一件事。** 连接诊断这类和 Web 无关的功能另行提交。
- **安全靠认证和授权，不靠关掉入口。** Web 首次默认关闭，由用户在桌面端选择是否启用：用户可能自动升级、不看新功能说明，不应在不知情时开放公网 Web 入口，开启即表示知道并需要它。选择持久保存，服务重启不重置。启用后，安全由标准的登录、会话和权限检查保证，不能用开关代替这些检查。

## 结构

### 端口与路由

服务端现有的监听已经在同一个端口上同时处理普通 HTTP（`/health`、`/client/installer`）和 WebSocket 升级（`/ws`）。Web 只在 HTTP 处理里增加路由：

- 页面与静态资源：入口路径下的 `/`、`/assets/*`。
- 登录相关接口：登录、退出、查询当前会话。
- 浏览器的 WebSocket：入口路径下单独一个地址，与桌面的 `/ws` 分开。

`/ws` 保持原有桌面认证与执行通道，不新开端口，防火墙规则和 Docker 端口映射不变。Web 默认关闭，在桌面设置中开启或关闭，服务端保存开关状态（见 #110 的讨论）。

页面由服务端提供，天然与服务端同版本，不存在桌面那种版本不一致的问题。Docker 镜像和服务端升级包携带同版本的前端构建，运行环境不引入 Vite、Electron 等开发依赖。

### 前端

浏览器与桌面共用同一套页面、组件和 `ProxyClient`。宿主差异集中在一处判断：浏览器没有本机目录、窗口管理、安装器、客户端升级等能力，相应入口隐藏。前端隐藏只是界面上的处理，能不能执行由服务端决定。

Web 设置的状态与操作放在设置相关的组件里，不进入 `ProxyClient` 的通用状态。

### 服务端作为一台设备

浏览器没有执行通道，它在服务端里是一个只有控制连接的操作端。第一版浏览器能做两类事：

1. **操作在线设备上已有的会话**：发消息、回答问题、审批、停止、打开终端，复用 #90 的跨设备能力。
2. **在服务端上直接对话**：Claude Code 本来就运行在服务端，这类会话不经过 SSH 去操作任何设备，工具在服务端容器里执行。

第二类会话归属于**服务端本身这台设备**，它始终在线，出现在“其他设备”列表里，桌面端也能看到并操作这些会话。不把每个浏览器当作一台设备：浏览器没有稳定身份，换浏览器或清除数据后，这台“设备”和它的会话就找不到了。界面上沿用“其他设备”现有的按设备、按项目分组和折叠（#102），不另做一套列表。

服务端会话的工作目录不由 Web 另行规定，跟随正在推进的云端项目对齐（见 #85 的讨论）：在项目下建的会话落到该项目在服务端对应的固定目录，记忆、`.claude/` 设置等自然按项目共享；没有项目的普通会话仍是一个会话一个目录。服务端设备上的项目就是服务端上的这些目录，不需要为 Web 再设计一套项目概念。

第一版不包括：浏览器新建或移动项目、在其他设备上新建或分叉会话、附件上传、定时任务。服务端设备上的项目随云端项目对齐一起提供；对齐落地之前，Web 在服务端设备上只建普通会话。

## 部署与证书

### 三种现有部署模式

| 部署模式 | 监听 | 浏览器访问 |
| --- | --- | --- |
| 自签证书（IP 加指纹） | 公网 HTTPS，自签证书 | 未受信任时由浏览器提示证书问题；页面只提示实际安全上下文和通行密钥功能限制，不以服务端证书推断反代入口的证书状态 |
| 真实证书（`--mode certificate`） | 公网 HTTPS，正规证书 | 直接可用 |
| nginx 反向代理 | 仅本机回环 HTTP | 由反向代理提供证书 |

不开放公网明文 HTTP：登录密码就是服务凭据，明文传输等于交出整个服务。

### 已有自签部署：在桌面端导入证书

桌面端按证书指纹校验服务端，直接替换服务端证书会让所有已连接的桌面断开。所以按 TLS 握手中的域名（SNI）选择证书，两张证书并存：

- 按 IP 访问或不带域名的握手，继续使用原自签证书，现有桌面连接和健康检查不受影响。
- 按指定域名访问的握手，使用导入的证书。按同一域名连接的桌面也会用这张证书，可改为 CA 校验。

导入只在桌面端进行，私钥不经过浏览器，也避免浏览器用自己所在的连接替换这条连接的证书。流程：

1. 在桌面设置里填写使用该域名的 Web 对外地址。
2. 粘贴或选择证书链与私钥文件。服务端用 Node 自带的 `X509Certificate` 校验有效期、域名覆盖、与私钥是否匹配、证书链签名，通过后保存。
3. 证书和私钥存为数据目录下权限 600 的两个文件，导入后对新连接立即生效，不需要重启。只保留当前这一份，不留旧私钥。
4. 界面显示域名、签发者和到期时间，到期前 30 天在客户端提醒；可以一键恢复为只用自签证书。

第一版不在客户端内自动申请证书（ACME）：Let's Encrypt 的域名验证需要 80 或 443 端口，而服务一般在 8787；公开证书的有效期也在逐年缩短，到 2029 年只有 47 天。需要自动续期的，推荐交给 Caddy、nginx 等反向代理。

### 已有 nginx 占用 80/443

推荐让 nginx 直接转发到服务端现有的 HTTPS 端口，用 `proxy_ssl_trusted_certificate` 信任自签证书。服务端部署模式不变，不新开端口，按 IP 加指纹连接的桌面不受影响。本机内多一次 TLS，开销可以忽略。客户端可以根据当前端口和证书指纹生成可复制的 nginx、Caddy 配置片段。

另一种做法是服务端再开一个只监听本机的 HTTP 端口给反向代理用。它只省掉本机内的一次 TLS，却多一个监听端口和一项配置，不采用。

### 来源地址与 `X-Real-IP`

登录限速按来源地址计数。经反向代理时，服务端看到的来源都是代理的地址，必须信任代理传来的 `X-Real-IP`，否则所有浏览器会被一起限速。

但这个信任必须是显式的：没有反向代理时，信任这个头就等于让任何人伪造来源绕过限速。约定如下：

- 默认不信任。在桌面设置里明确打开“前面有反向代理”，并填写受信任的代理来源地址后，才采用来自这些地址的请求所带的 `X-Real-IP`；其他来源的这个头一律忽略。
- 不能只按“来自 127.0.0.1”判断。Docker 映射端口时，宿主机上的 nginx 访问容器，服务端看到的来源往往是 Docker 网桥的网关地址，而不是回环地址。
- 现有的 nginx 部署模式保持原有行为。

## 登录与安全

### 登录

- 密码是服务凭据 `PROXY_TOKEN`，沿用现有按来源地址的失败限速。
- 可选验证器二次验证（TOTP，RFC 6238），界面里推荐开启。Bitwarden、1Password 及常见手机验证器都支持存入和自动填写。
  - 开启时显示二维码和密钥文本，用户必须输入一次正确的动态码，验证通过才算开启成功。
  - 同一时间窗口内用过的动态码不能再次使用，动态码错误同样计入失败限速。
  - 丢失验证器时，可以在桌面端关闭二次验证；桌面端靠凭据和证书指纹连接，不受影响。是否另外提供恢复码待定。
  - 二次验证只用于 Web。桌面断线后会自动重连，不适合每次输入动态码。
- 登录成功后服务端新生成会话 ID，写入 Cookie：`HttpOnly`、`Secure`、`SameSite=Strict`，`Path` 限定在入口路径下。服务端只保存会话 ID 的哈希，存在现有 SQLite 数据库的新表里。
- 每条会话记录当时服务凭据的指纹，凭据更换后所有浏览器会话立即失效。
- 退出登录时，服务端作废会话并关闭该会话的连接。

### 会话有效期

- 无操作 2 小时自动退出，可以在设置里调整（15 分钟到 24 小时）。Web 端多是用手机顺手看看进度、干预一下，不需要很长。
- 另设 30 天绝对上限，到期必须重新登录。
- 由服务端判定。“操作”只算用户主动发出的命令，服务端推送和自动重连不算。

### 安全子入口路径

- 默认使用根路径。设置子路径后，根路径和其他路径一律返回空的 404。
- 桌面端或已登录的浏览器都可以修改，修改时要求重新输入密码和动态码。
- 子路径用来减少被扫描发现的机会，访问控制仍靠登录。

### 权限在服务端

- 浏览器能执行哪些命令，由服务端白名单决定；协议里新增的命令默认不对浏览器开放。参数一律经 zod 校验。通过浏览器开发者工具修改请求无法绕过。
- 浏览器连接不能发送执行通道和设备身份相关的帧。
- 安全相关设置（开关二次验证、修改子路径、撤销其他会话）要求重新验证身份。
- 设置里可以查看已登录的浏览器会话并单独撤销。

### 标准 Web 防护

| 风险 | 措施 |
| --- | --- |
| 跨站请求伪造 | `SameSite=Strict`；登录接口和 WebSocket 握手校验 `Origin` 与 `Host` 一致 |
| XSS | CSP；React 默认转义；Markdown 渲染保持 `skipHtml` |
| 点击劫持 | `frame-ancestors 'none'` |
| 协议降级 | HTTPS 下发送 HSTS |
| 暴力破解 | 密码和动态码共用失败限速 |
| 会话固定 | 登录成功后重新生成会话 ID |
| 路径穿越 | 静态文件先解析真实路径，再检查是否在资源目录内；不提供 source map 和目录列表 |
| 注入 | SQL 全部参数化；输入全部经 zod 校验 |

### 已知风险

服务端上的会话里，Claude Code 与服务程序是同一个 Linux 用户，能读到服务端配置，包括服务凭据。登录 Web 本身就需要这个凭据，对使用者本人不构成越权；风险在于 Claude 处理外部内容时可能被提示词注入诱导读取并泄露它。这不是高频高危风险，第一版只在文档中记录；用独立系统用户或容器隔离留作后续方向。

## 对 #101 的评估

可以借鉴的思路：

- 服务端的浏览器命令白名单。
- 前端按宿主能力区分桌面与浏览器。
- 静态文件服务的路径检查方式。
- Docker 和服务端升级包携带前端构建。

不应沿用的部分：

- **配对码流程和无期限的浏览器授权。** 改为凭据登录加可选二次验证，会话有空闲超时和绝对上限。
- **Web 开关只存在内存里，服务端重启后自动关闭。** 这是用关掉入口代替安全设计。
- **证书导入的实现方式。** 按 SNI 选证书是对的，但手写 DER 解析器、内存 TLS 握手验证、revision 并发控制都没有必要；存储里的 `previous` 字段每次保存旧私钥却从不读取。
- **为从未发布过的“旧版服务端”写的兼容。** `ready` 消息里的 6 个能力标志、`external-links.cjs` 的 `legacy` 分支、客户端里对“旧服务不发送剩余时长”的处理，以及文档里多段相应说明。
- **连接诊断。** 与 Web 无关，约 650 行，应另提。
- **共享核心被侵入。** `ProxyClient` 增加了 12 个 Web 状态字段和设置页专用的加锁、倒计时逻辑；`server.ts` 内联了约 300 行 Web 命令处理；`WebAccess` 构造函数有 7 个位置参数。
- **已有路径的行为改动。** 诊断协议对所有连接开启、健康检查改 `servername`、桌面对其他设备的会话显示 SessionBar、终端和刷新的禁用条件、`/ws` 以外的升级请求从 403 改为 404。即使其中有合理的修复，也应单独提出。
- **存储分散。** 浏览器授权放在数据目录根下，导致会话存储的旧数据导入要特意排除它；设置和证书又放在另一个目录。
- 测试约 8000 行，大量用于覆盖上述多余设计带来的并发和恢复分支。

## 待定

- 二次验证是否提供恢复码。
- 客户端内自动申请证书。
- 服务端会话用独立系统用户或容器隔离。
