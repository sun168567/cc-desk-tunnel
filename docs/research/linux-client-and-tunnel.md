# Linux 客户端、WSS 隧道转发与多设备：评估记录

2026-10-08 评估，起因是 [#9](https://github.com/sun168567/cc-desk-tunnel/pull/9)。它一次带来了 Linux 图形客户端、终端客户端 `ccdt`、经 WSS 的执行通道、断线续接、多 agent 和后台常驻。本文记录每一项的判断和判断的理由，结论本身只占一小部分。

方法：读完全部提交并对照当前主线的对应实现；能实测的在一套现有的 Windows 部署上测了。**Linux 客户端没有运行过**，涉及它实际表现的判断来自读代码，文末单列为未验证。

## 总的取向

支持第二个平台时，差异应当尽量在源头消掉，而不是在各处留分支。能做到这一点的地方比预想的多：

- Electron 已经抹平了绝大部分界面与系统集成。只看 #9 的第一个提交，一个完整的 Linux 图形客户端只需要约 250 行产品代码。
- 执行通道换成 WSS 之后，两端用同一套通道。
- 提示词合成一份，设备变化只追加一句。
- 名字按角色起而不是按平台起，就不需要为另一个平台解释。

真正要分平台的只剩少数几个接口相同的小模块（SSH 服务端的启动、命令外壳、子进程清理、凭据保存），以及打包、升级和验证。后三样是持续的负担：每次发版多一个产物，多一个系统要测。所以 Linux 先按实验性支持，只以一个参考系统（最新的 Ubuntu LTS，x64）为准，其余留给使用者从源码构建。

## 执行通道：WSS 隧道转发代替 frp

**判断：采用，并且两端统一，去掉 frp。**

它是等效的。转发只做字节对接：服务端在回环口收到 `ssh` 的连接，接到客户端预先建立的一条 WSS 连接上，不解析 SSH。对 Claude 来说没有变化，仍是一个 SSH 配置文件加一个回环端口。

只让一个平台走 WSS 是最差的状态，因为服务端要长期维护两种通道。统一之后可以去掉 frps、frpc、单独的公网端口和隧道证书。

连接模型比较过三种：每条 SSH 连接独占一条 WSS 并由 SSH 自己做连接复用；在一条 WSS 内自己实现多路复用；把 SSH 数据放进控制连接。选第一种，也就是 #9 的做法。自己做多路复用要实现流编号和逐流的流量控制，那是最容易出错的部分，而 SSH 的连接复用是现成的；放进控制连接会让大文件传输拖慢界面消息和心跳。

既然转发是自己写的，就要知道它的开销。按 #9 的做法写了一个测量脚本，在本机回环上用三个线程分别扮演命令发起方、服务端一侧和客户端一侧：

| 路径 | 客户端→服务端 | 服务端→客户端 | 小包往返 |
| --- | --- | --- | --- |
| 直连 TCP | 1534 MiB/s | 1597 MiB/s | 0.03 ms |
| WSS 转发 | 405 MiB/s | 667 MiB/s | 0.09 ms |

这是转发代码的处理上限，不含真实网络。它比常见的公网链路速度高出近两个数量级，瓶颈在网络而不在转发。两个方向不对称，是 WebSocket 规定客户端发出的数据要做掩码运算造成的。

连接复用是一项独立的收益，与通道无关：在现有通道上实测，每条命令从 0.6–0.8 秒降到 0.13–0.2 秒。两端都应当打开。

中断时的表现与 frp 相同。SSH 协议本身不能续接，承载它的连接一断，进行中的命令就失败。要改变这一点得在隧道层做续传，属于“断线续接”一节的范围。

## Linux 上的 SSH 服务端：进程内实现

**判断：用进程内实现（ssh2），不用真实 sshd。**

最初的倾向是真实 sshd：SSH 通道对 coding agent 很重要，应当给它最习惯的环境。比较之后发现，在 Linux 上真实 sshd 并不自动带来这个环境。

| 方面 | 进程内实现 | 真实 sshd |
| --- | --- | --- |
| 可执行文件的来源 | 随包的纯 JS 依赖 | Ubuntu 桌面默认没有 sshd |
| 命令的环境 | 继承客户端进程，带桌面会话的变量 | 很空：没有图形显示、D-Bus、SSH agent、代理 |
| 断开时清理子进程 | 杀整个进程组 | 无终端的命令断开后不杀子进程 |
| SFTP 与默认模式的 `scp` | 需要补 | 有 |
| 协议实现 | 成熟的库，服务端角色用得相对少 | 参考实现 |

真实 sshd 的代价有三处。可执行文件要么依赖系统包，那会顺带装上并启用一个监听 22 端口的系统服务，违反“本机不留常驻组件”；要么随包带一份，那要自己编译并绑定发行版版本。清理语义是反的，要另写包装。环境要逐个变量注入，没有 SSH agent 时用带口令的密钥推送代码会失败。

进程内实现缺的主要是 SFTP 和使用者的 shell 环境，补起来更轻：

- **SFTP**：把子系统请求交给系统的 `sftp-server`，安装包只依赖这一个可执行文件，不带服务。
- **登录 shell**：用使用者自己的，不固定为 bash。
- **完整环境**：Linux 上很多开发工具在 shell 的启动脚本里把自己加进 PATH，而这些脚本只在交互式终端里完整执行，所以使用者在终端里能用的命令，经 SSH 执行却找不到。做法是连接时以登录加交互方式运行一次使用者的 shell，记下环境，之后的命令都用它。

权限不需要另外处理：命令以桌面当前用户的身份运行，不能提权。

两端的 SSH 服务端是两个接口相同的小模块。日后若发现协议层的问题，替换是局部的。

## 提示词：一份，而且短

**判断：一份与平台无关的提示词，约 8 行；设备变化时只追加一句；主机别名按角色命名。**

系统提示词一变，模型侧的提示缓存从它之后全部失效。主线为此已有一套做法：会话的系统提示词在压缩之前逐字不变，变化随下一条用户消息告知。按平台各写一套提示词与这套做法相冲突，换设备时提示词必然变化，而且每次调整操作说明都要改两处。

合成一份之后，两个平台的操作要点各占半行，一直都在。设备变化时只需要告诉模型换成了什么系统、项目目录在哪。

能这么短，是因为随设备变化的值可以从源头减少。本机 SSH 服务进程的环境变量会传给它执行的命令，所以 PowerShell 的完整路径可以换成“把随包目录放进 PATH”，定时任务文件的位置可以换成一个环境变量。剩下的只有系统名称和项目目录。对当前的模型，短而明确的提示词效果不比长的差，其余可以交给模型自己判断。

别名。`ssh` 命令必须有一个目标参数；连接参数都在配置文件里，归在一个名字下面。这个名字必须有，但它只是一个标签。按平台起名才需要在另一个平台的提示词里解释，按角色起名（`device`）就不存在这个问题。

## 设备与并发

**判断：允许同一使用者的多条连接，各带各的执行通道；运行和终端合计一个按内存推算的上限。**

“同一时间只接受一台设备”是一条策略，不是结构上的限制。服务端本来就是按多条连接写的，每个运行用的是发起它的那条连接的执行通道。这条限制原先有实际理由：每条连接要起一个 frps 进程和一个端口。换成 WSS 隧道转发后，每条连接的通道只是服务进程里的一个回环监听。

三个层次各自独立：

| 层 | 规则 |
| --- | --- |
| 连接 | 允许多条 |
| 会话 | 同一时间最多一个运行或终端，属于发起它的连接；别的连接可以看、不能发；结束后谁都可以接着发 |
| 资源 | 运行和终端合计一个上限，对所有连接合并计算 |

项目仍是单用户，只是这个人可以同时连接自己的多台设备。图形客户端与终端客户端同时在线、几个终端里各开一个终端客户端、两台机器同时在线，都由此解开。新带来的情况是会话的项目路径属于某一台机器：会话记下创建它的设备，列表默认只显示本机的，从另一台设备接着发时用变化提醒告知模型。

终端从全局唯一改为每个会话一个，与此是同一个方向，不涉及对 CLI 的任何改动。

设备数和 CLI 进程数是两个独立的量。多一条连接几乎不占资源，占内存的是 CLI 进程：实测一个运行中的 CLI 进程常驻内存在 250 MB 以上，以 1 GB 内存的服务器为例，两个就接近上限。所以上限不能是一个固定的数，默认值按“（总内存 − 300 MB）÷ 300 MB”推算，并做成设置项。这个常数只有一个实测点，实现前要多测几种情况。

## 终端客户端

**判断：基本形态进入主线；列表、worktree、通知和后台常驻暂不进。**

`ccdt` 的核心很小。服务端本来就能在伪终端里运行未修改的 CLI 并带上远程提示词，图形客户端的内嵌终端用的就是它；`ccdt` 把它接到使用者自己的终端。这是合适的形态：把原版 CLI 桥过来，复用同一条执行通道。

其余部分暂不进，考虑是：

- 图形客户端已经有并行会话和状态显示。终端一侧的列表把会话管理又实现了一遍，以后每个相关功能都有两处界面。它是为“以终端为主要界面”的用法设计的，而主线目前以图形客户端为主。
- 后台常驻会一直占着唯一的设备名额。多连接落地后这个问题不再存在，届时再看。

Windows 上也希望有终端客户端，但有一个实测到的约束：Linux 上它借包内的 Electron 以 Node 方式运行，这在 Windows 上行不通。同样的伪终端条件下，打包的客户端程序以 Node 方式运行时输出端是终端、输入端不是；普通的 `node.exe` 两端都是。所以 Windows 上需要自带一个控制台程序形态的运行时，并且要跟着图形客户端的安装包一起安装和升级，因为它的协议版本必须和服务端一致。它排在 Linux 版之后，但代码从一开始就不应带只认 Linux 的假设。

## 断线续接

**判断：单独做，放在后面；做法届时再比较。**

现在连接一断，服务端就结束这条连接名下的运行。会话和上下文都在服务端，重新连接后可以接着做；丢的是进行中的那一轮、等待中的审批和一次手动重连。

有两种做法。#9 是传输层续接：两端给每一帧编号并保留未确认的帧，断线后自动重连、互相补发。另一种是应用层接管：服务端给断线连接名下的运行留一段宽限期，同一台设备重新连上来时接管它们，按已有的事件序号补上漏掉的内容。后者只是设想，没有代码。

| 方面 | 传输层续接 | 应用层接管 |
| --- | --- | --- |
| 短暂断网，客户端还活着 | 全部续上，包括终端 | 运行续上，终端结束 |
| 客户端重启或崩溃 | 续不上 | 宽限期内能接回 |
| 断网期间 Claude 发起的命令 | 等待 | 直接失败 |
| 新增的机制 | 一套帧编号、缓存、重放 | 运行的宽限期与接管 |
| 对连接桥的改动 | 大 | 小 |

两者各有覆盖不到的情况，没有哪个明显更好。它影响的是体验而不是能否使用，却要改最关键的连接路径，所以等前面几项稳定后单独做。

## 安全

去掉 frp 之后攻击面是减少的：公网少一个端口，服务端少一个进程，客户端少一个可执行文件。

新增的公网入口只有凭密钥接入的隧道连接。读代码的结论（不是正式审计）：密钥是每条连接随机的 256 位值，经已认证的控制连接下发，客户端核对证书指纹之后才发出去；比对是常量时间的，密钥错误计入来源地址的限速；隧道连接收不到任何广播，发来的协议消息一律忽略。即使密钥泄露，拿到的只是冒充桌面一端接收 SSH 连接的位置，而 SSH 客户端固定校验主机密钥，冒充者完成不了握手。

多连接之后要重新核对每个地址的未认证连接上限，因为每个客户端启动时要同时开一条控制连接和两条隧道连接。

## 未验证

- Linux 客户端的全部实际表现，包括自绘标题栏和系统通知。
- 进程内 SSH 服务端对保活请求的应答；把 SFTP 子系统交给外部程序的实际效果。
- WSS 隧道转发在真实网络上与 frp 的对比，以及丢包、高时延和反代下的表现。
- 8 行提示词在真实会话里的效果，以及 Windows 那半行操作要点能否再省。
- CLI 进程在不同负载下的内存占用。
- 终端客户端在各种 Windows 终端里的输入表现。
