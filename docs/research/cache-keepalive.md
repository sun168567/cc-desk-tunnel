# 提示缓存保活（评估记录）

2026 年 10 月整理，来自 [#29](https://github.com/sun168567/cc-desk-tunnel/issues/29)。尚未实现；这里记下背景、做法和动手前要先确认的事。

## 背景

- 每次请求都会把整段对话重新发给模型。与上一次相同的前缀按“缓存读取”计费，约为正常输入价的十分之一（各模型不同）。
- 缓存有有效期：5 分钟或 1 小时（设置 → CLI 设置 →“提示缓存时长”）。有效期内每次命中都会重新计时，不另收费。
- 过期后的下一条消息要把整段上下文重新写入缓存，写入价高于正常输入价（5 分钟档 1.25 倍，1 小时档 2 倍）。上下文几十万 token 时，隔一个多小时再发一句话，这一句就可能占掉订阅 5 小时额度里可观的一部分。
- “保活”是在缓存过期之前发一次很便宜的请求去命中它。每次只付一次整段上下文的读取价。

## 为什么现在没有

- 续期需要在有效期内有请求命中缓存。本项目每一轮运行启动一个 Claude Code 进程，这一轮结束进程就退出，两轮之间没有请求。
- 官方 API 文档里“不产生输出的预热请求”只能直接调用 API，经 Claude Code 发不出来。
- 随服务端安装的 Claude Code（2.1.293）程序里能看到一套内置的续期逻辑，由官方的远程开关控制，没有公开文档，也只在进程运行期间有效。不能依赖它，也不应直接调用它用的内部接口。

## 打算怎么做

做成每个会话一个开关，默认关闭。开启后，在会话空闲接近缓存有效期时，向会话发一条很短的真实消息。

- **复用定时任务的发送通道**：定时任务已经能按间隔向指定会话发消息。保活需要在它之上补四样：
  1. 次数或截止时间（例如“保活 4 小时”），到了自动停。
  2. 按空闲时间触发：距这个会话上一次活动接近有效期才发，用户刚发过消息就不发。
  3. 专门的消息形态：提示词要求模型只回一个字、不做任何操作；界面上折叠成一个标记，做法同“继续”。
  4. 会话正在运行时跳过。
- **不能改模型和推理强度**：保活消息必须沿用会话当前的设置，改任何一项缓存就失效。
- **只在缓存时长为 1 小时时有意义**：5 分钟档要每 4 分钟发一次，不值得。
- **客户端发还是服务端发**：定时任务由客户端发送，只覆盖“人离开、客户端还开着并连接”的情形。放到服务端可以覆盖客户端关闭的情形，但现在发起一轮运行要求设备在线，改动大得多。先做客户端这一种。

## 代价

- 每次保活按缓存读取价计一次整段上下文，外加启动一次 CLI 和几个字的输出。以 30 万 token、Opus 5.5 估算，每次约 0.06 美元，过期后重写一次约 2.4 美元；订阅账号按同样比例占额度。
- 对话里每次多两条很短的消息，上下文随之略增。
- 订阅的额度窗口已过期时，保活消息会开启新的 5 小时窗口。
- 额度已经用完时它帮不上。

## 使用政策与账号风险

动手前和上线时都要重新核对官方条款，下面是 2026 年 10 月读到的内容，不是法律意见。

- 用 API 密钥或第三方接口时，保活就是自己付费的普通请求，官方缓存文档本身讲了如何续期和预热，没有疑问。
- 用订阅账号（Pro / Max）登录时有风险：
  - 消费者条款禁止以自动或非人工的方式访问服务，除非使用 API 密钥或官方明确允许。
  - Claude Code 的[法律与合规](https://code.claude.com/docs/en/legal-and-compliance)页写明，订阅的额度按“普通的个人使用”设定，并保留不经通知采取限制措施的权利。
  - 保活消息是程序定时发出、只为占住缓存的请求，很难算作普通的个人使用。官方自己的续期由服务端开关决定是否允许，自行发消息续期等于绕开了这层控制。
- 因此：开关默认关闭；开启时在界面上说明它会定时自动发送消息、会消耗额度，订阅账号使用可能不符合官方条款并带来账号风险；文档里同样写明。是否对订阅账号直接不提供这个开关，实现时再定。
- 现有的定时任务同样是自动发送，适用同一条提醒。

## 动手前先确认

1. 用官方账号、1 小时缓存，在一个会话上建间隔 50–55 分钟的定时任务，隔一小时后看调用统计里那条消息是缓存读取还是写入。确认缓存确实续上。
2. 同一条件下不建任务，一轮结束后隔一小时再发消息，确认官方内置的续期在本项目的运行方式下确实不起作用。
3. 重新读一遍当时的消费者条款和法律与合规页。
