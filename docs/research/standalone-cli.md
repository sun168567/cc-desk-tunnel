# 独立终端客户端 `ccdt`：设计与任务

2026-11-01 立项。起因是 [#136](https://github.com/sun168567/cc-desk-tunnel/issues/136)：社区实测经 SDK 运行时 5 小时额度消耗更快，使用者希望有一条完整的交互式 CLI 路线。[#139](https://github.com/sun168567/cc-desk-tunnel/pull/139) 给出过一种做法（普通 SSH 加 `docker exec` 进容器），它绕开了现有的 WSS 连接，需要服务器账号与 docker 权限，本方案取代它。

jiangan-code 的分支（[jiangan-code/cc-desk-tunnel](https://github.com/jiangan-code/cc-desk-tunnel)，#9 之后在 10-07 的主线上继续做的 Linux 版 `ccdt`）实际解决过其中几个问题，下文采纳的部分注明出处，移植时按当前主线改写并注明作者。它基于旧主线（单执行设备、旧执行通道），不能直接合入。

本文先写设计和判断的依据，最后是任务清单，做完一条划掉一条。标“待验证”的判断来自读代码，推进到那一步时先验证再动手。

## 目标与边界

- **独立的终端客户端**，不依赖图形客户端安装或运行。仓库里与图形客户端放在相邻位置，尽量共用代码。
- **Claude Code 的 TUI 原样透传**：显示和按键一比一中继，不改造、不注入按键。增强只放在 TUI 外面，以子命令的形式提供，与图形客户端的项目、会话概念一致。
- **会话与图形客户端打通**：终端里能接续图形客户端的会话；终端里聊的内容，图形客户端的上下文和记录里都要有。
- **用量统计打通**：终端的调用计入同一份统计。
- **身份是交互式 CLI**：终端路线不能被识别成 SDK 调用，见“CLI 与 SDK 的身份边界”。
- **本次不改图形客户端的内嵌原生终端**。等 `ccdt` 可用后再决定是否用它取代内嵌终端。因此服务端的新行为一律由 `ccdt` 显式请求才生效，内嵌终端打开时行为不变。

## 已有的基础

| 需要的能力 | 现状 | 代码 |
| --- | --- | --- |
| 经 WSS 中继终端 | 已有一组终端消息：原始字节、窗口尺寸、按字节确认的流控（128 KB 暂停，32 KB 恢复） | `apps/server/src/native-terminal.ts`、`server.ts` 的 `openTerminal` |
| 设备执行通道 | 连接桥、通道分发、Windows 与 POSIX 的 SSH 服务端都是纯 Node 模块，不依赖 Electron | `apps/desktop/electron/proxy-bridge.mjs` 及其引用的 `.mjs` |
| 同一台电脑多个连接 | 服务端按设备 ID 建席位，一个席位可挂多个连接；执行通道用最后连上的那个，它断开时切回其余的 | `server.ts` 的 `seat`/`vacate` |
| 项目与会话 | 列表、订阅、新建都在现有协议里 | `packages/protocol` |
| 用量统计 | 终端进程已注入遥测变量，请求记录进入同一个统计库 | `server.ts` 设置 `options.claude.environment`，`usage.ts` |

#9 的评估记录里有一条实测约束：Windows 上把打包的 Electron 当 Node 运行时，输入端不是终端，raw 模式用不了（见[评估记录](linux-client-and-tunnel.md#终端客户端)）。独立客户端自带控制台程序形态的 Node 运行时，这个问题不存在。

## 形态与仓库位置

- `apps/cli`：`ccdt` 本体，Node 24，与服务端一样直接运行 TypeScript 源码。
- 连接桥及其依赖（`proxy-bridge`、`tunnel-channels`、`windows-ssh`、`posix-ssh`、`ssh-keys`、`system-proxy`、`connect-errors` 等）从 `apps/desktop/electron` 移到一个共享包，图形客户端和 `ccdt` 都引用它。这一步只搬代码不改行为，图形客户端的打包配置要跟着改。
- 协议版本必须和服务端一致。`ccdt` 连接时检查版本，不一致时提示升级。它和图形客户端各自升级，互不牵连。
- 分发形态（npm 包、自带运行时的压缩包或安装包）留到功能可用后再定。Windows 上还要带 OpenSSH 的 sshd，图形客户端安装包现在是自带的。

## 连接、登录与设备身份

- `ccdt login <地址>`：在终端里输入 Token（不回显），可选保存；也支持 `--token-stdin` 和 `CCDT_TOKEN` 环境变量。服务地址和证书指纹默认取图形客户端保存的值。可以保存多个服务端，与图形客户端的“多个连接”对应。
- **设备身份**：本机装有图形客户端时，读取它的 `settings.json` 里的 `deviceId`，服务端就把两者视为同一台设备；没有装时由 `ccdt` 自己生成并保存。
- **复用图形客户端保存的登录**（待定）：图形客户端用 Electron 的 `safeStorage` 加密 Token。Windows 上可以用 DPAPI 解开，但这依赖 Chromium 的内部存储格式；macOS 上读钥匙串会弹出授权框。推进到这一步时再比较各种做法。
- **两个进程都在线时**（待验证）：两个客户端各自运行一个本机 SSH 服务端，要确认端口和主机密钥不冲突，并且执行通道在两者之间切换时正在执行的命令不受影响。

## 会话连续性

结论：可以做，而且大部分是现成的。有一个前提要先验证；另外有几种情形只能做到“如实提示”，需要确认是否可以接受。

### 上下文：同一个原生会话，天然连续

- 图形客户端的每一轮经 SDK 运行。原生会话 ID 就是本项目的会话 ID：第一次用 `sessionId`，之后用 `resume`。CLI 的会话记录存在 `nativeRoot` 对应的目录下（`server.ts:548`、`claude.ts:184`）。
- 内嵌终端在同一个目录、同一个 HOME 下启动 CLI，但现在没有带会话参数，每次都是一段新会话。
- `ccdt` 打开终端时，服务端改为：会话已有原生上下文就带 `--resume <会话 ID>`，否则带 `--session-id <会话 ID>`。这样终端里的每一轮写进同一份 CLI 会话记录。图形客户端下一轮 `resume` 时读到的就是包含终端对话的完整上下文。上下文不需要额外同步。
- **前提（已验证，见文末“验证记录”）**：交互式 `claude --resume <id>` 在原会话 ID 下续写，不另起 ID；SDK 的 `resume` 和交互式 CLI 可以交替续写同一个会话。
- 终端第一次建立原生会话时，服务端要补记一个 `native.session` 事件。`hasNativeContext` 靠这个事件判断，否则图形客户端下一轮不会 `resume`。

### 记录：终端结束时，把新增的对话导入图形客户端

- 图形客户端显示的是本项目自己的事件记录，由 `ClaudeStream` 把 SDK 消息转换而来。终端里的对话不经过它。
- 做法：
  1. 服务端打开终端时，用 SDK 的 `getSessionMessages` 记下原生会话最后一条消息。
  2. 终端结束时（无论哪个客户端打开的），再读一次，取出这条之后的消息。
  3. 把这些消息交给同一个 `ClaudeStream` 转换成事件，标明来自终端。
- 好处：
  - 只有一条转换路径，图形客户端看到的终端对话和自己运行的对话格式相同。
  - 读取用的是 SDK 的公开接口，不自己解析会话文件。
  - 工作都在服务端，`ccdt` 和以后的内嵌终端都适用。
- 导入的内容不如实时运行完整：没有流式过程，也没有审批记录，终端里本地命令的输出（例如 `/usage` 面板）也看不到。导入的只有消息正文、工具调用和结果。
- 实现：`apps/server/src/terminal-transcript.ts`。打开时记下原生会话已有的全部消息 ID，结束时导入其余的。压缩会在摘要之后保留一部分旧消息，按 ID 排除后不会重复显示。压缩摘要由 `isCompactSummary` 识别，记成一次压缩；CLI 自己写的说明（`is_meta`）和不是使用者输入的消息（`origin.kind` 不是 `human`）不导入；本地命令显示为命令本身和它的输出。这些字段 `getSessionMessages` 都会带上，2026-11-01 用 CLI 2.1.293 实测过。
- 会话切换由 SessionStart hook 记录：终端用一份自己的设置文件，内容是服务的提供方设置加上这个 hook，`--settings` 改为指向它。这个文件和 hook 写入的记录放在数据目录的 `terminals/` 下，权限 0600，终端结束时删除，服务启动时整个目录清空。
- 时机先做“终端结束时导入”。终端运行期间在图形客户端里实时看到进度，留到以后再做。

### 只能如实提示的情形（需要确认是否接受）

| 终端里的操作 | 后果 | 打算的处理 |
| --- | --- | --- |
| `/clear`、`/resume` 到别的会话、新开会话 | CLI 换了原生会话，之后的对话不在这个会话里 | 只导入切换之前的部分，并记一条提示。切换由 CLI 的 SessionStart hook 发现：`/clear`、`/resume` 之后它报告新的 `session_id`（jiangan-code 分支的做法：hooks 写进原生目录的 `.claude/settings.local.json`，保留使用者自己加的 hooks） |
| 回退（`/rewind`、双击 Esc） | 原生会话从某处分叉，图形客户端已显示的部分内容不再在上下文里 | 记下的最后一条消息不在当前链上时，记一条“终端中回退了对话”的提示，再从分叉点导入。事件记录只追加，旧内容保留 |
| `/compact` | 上下文压缩 | 读取时带上系统消息，转换成已有的压缩事件 |

同一个会话不能同时在图形客户端和终端里运行，现有的“忙碌”锁已经保证了这一点。来回切换的意思是：一边结束，另一边接续。

## 终端在服务端常驻

采纳 jiangan-code 分支的做法：

- 服务端给每个终端维护一份屏幕状态（`@xterm/headless` 加 serialize 插件）。客户端接入时先发当前整屏，再接实时输出；同时恢复键盘模式（kitty 键盘协议、modifyOtherKeys）、鼠标编码和光标显示。
- 客户端 30 秒不确认输出，或者连接断开，只断开显示，CLI 继续运行；之后任何一端都可以重新接入。只有明确结束（`/exit` 或关闭命令）才结束 CLI。
- 状态由 `Notification`（权限确认、提问）和 `Stop` hooks 得出：运行中、等你、空闲。图形客户端可以据此显示终端会话的状态。
- 常驻要设上限和回收：没有任何客户端接入的终端，空闲多久后结束，推进时定。
- 这些只对 `ccdt` 打开的终端生效。内嵌终端仍然随页面关闭而结束。

`ccdt` 本地还要做到：异常退出时恢复本机终端的状态（光标、括号粘贴、鼠标与焦点上报、备用屏幕）；输出接管道时不被截断（该分支修过 64 KB 截断）。

## 用量统计

- 终端进程已经带上了遥测变量。改用 `--resume`/`--session-id` 之后，CLI 上报的会话 ID 就是本项目的会话 ID，统计按会话归属自动对上（待验证）。
- `ccdt usage` 复用现有的统计查询消息。
- 测试只覆盖会话归属这一项。

## CLI 与 SDK 的身份边界

社区报告经 SDK 和 `-p` 调用时 5 小时额度消耗更快（官方未确认）。SDK 识别自己用的是子进程环境里的 `CLAUDE_CODE_ENTRYPOINT=sdk-ts`，它只写在传给子进程的环境副本里（SDK 0.3.286），不会改变服务进程自己的环境。终端路线遵守以下几条，并在代码里写明原因：

- 只在伪终端里以交互方式启动官方 `claude`。不经过 SDK 的 `query()`，不用 `-p`、`--output-format`、`--input-format`。
- 启动环境主动去掉 `CLAUDE_CODE_ENTRYPOINT` 和 `CLAUDE_AGENT_SDK_*`，防止从别处继承进来。
- 只用普通的交互式参数：`--resume`/`--session-id`、`--model`、`--effort`、`--settings`、`--permission-mode`、`--append-system-prompt`。
- 不用程序按键驱动 TUI。
- 一个单元测试检查最终的环境和参数。开发实测时抓一次请求头对比 User-Agent，确认终端是 `cli`、图形客户端是 `sdk-ts`。

图形客户端那条路仍然经过 SDK，这一点不变。

## 不采纳的部分

jiangan-code 分支里另有这些，不进本方案：终端里的 agent 列表、worktree、Herdr 集成、本机后台服务（daemon）、按线路选择的 SSH 转发（`ccdt-tunnel`）；断线恢复后自动提交一条提示让 Claude 继续（违背不注入输入）；多个 Claude 账号轮换与 Codex 账号池（与[路线图](../roadmap.md#明确不做)对订阅用法的约束相冲突）。

## 推进时再定的事项

- 运行中的前缀键，比如用来分离终端或切换会话；具体要哪些功能。jiangan-code 分支用 Ctrl+Q 回到列表，要确认不和 Claude Code 自己的按键冲突。
- 在项目目录里直接运行 `ccdt` 时，按真实路径找到这个项目最近的会话（该分支的做法），还是总要显式指定。
- 无人接入的终端保留多久。
- 复用图形客户端登录的做法；Token 在三个系统上的保存方式。
- 分发形态与升级方式。
- `ccdt` 可用后，内嵌原生终端是否由它取代。

## 验证记录

### 2026-11-01：会话 ID 与请求身份

在测试机的临时容器（`node:24`）里，用 CLI 2.1.293 和 SDK 0.3.286，对着一个本地模拟的 Messages 接口运行，不消耗真实额度。交互式 CLI 由伪终端驱动，和服务端的原生终端一样。

| 步骤 | 结果 |
| --- | --- |
| 交互式 `--session-id S` 聊一轮 | 会话记录 `S.jsonl` |
| 交互式 `--resume S` 再聊一轮 | 仍写入 `S.jsonl`，没有新文件 |
| SDK `query({ resume: S })` 一轮 | 初始化和结果都报告会话 `S`，写入 `S.jsonl` |
| 交互式 `--resume S` 聊一轮，`/clear`，再聊一轮 | `/clear` 之前的一轮写入 `S.jsonl`；之后的写入新会话，退出时提示的接续 ID 也是新的 |
| `getSessionMessages(S)` | 依次是前四轮的问与答，SDK 那一轮夹在中间，顺序正确 |
| SessionStart hook | 依次报告 `startup`、`resume`、`resume`、`clear`，`clear` 带着新会话的 ID |
| 请求头 User-Agent | 交互式为 `claude-cli/2.1.293 (external, cli)`；SDK 为 `claude-cli/2.1.293 (external, sdk-ts, agent-sdk/0.3.286)`。两者的 `x-app` 都是 `cli` |

结论：会话连续性的前提成立；`/clear` 的切换能由 hook 准确发现；交互式终端的请求身份是 `cli`，与 SDK 可以区分。测试容器和拉取的镜像已删除。
