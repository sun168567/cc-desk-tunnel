# 独立终端客户端 `ccdt`：设计与任务

2026-11-01 立项。起因是 [#136](https://github.com/sun168567/cc-desk-tunnel/issues/136)：社区实测经 SDK 运行时 5 小时额度消耗更快，使用者希望有一条完整的交互式 CLI 路线；更早的 [#97](https://github.com/sun168567/cc-desk-tunnel/issues/97) 也希望像 SSH 上去一样使用完整的 Claude Code。[#139](https://github.com/sun168567/cc-desk-tunnel/pull/139) 给出过一种做法（普通 SSH 加 `docker exec` 进容器），它绕开了现有的 WSS 连接，需要服务器账号与 docker 权限；[#140](https://github.com/sun168567/cc-desk-tunnel/pull/140) 在它的基础上修正后实测可用。本方案取代它，用量接入统计的需求沿用。

jiangan-code 的分支（[jiangan-code/cc-desk-tunnel](https://github.com/jiangan-code/cc-desk-tunnel)，#9 之后在 10-07 的主线上继续做的 Linux 版 `ccdt`）实际解决过其中几个问题，下文采纳的部分注明出处，移植时按当前主线改写并注明作者。它基于旧主线（单执行设备、旧执行通道），不能直接合入。

本文先写设计和判断的依据，最后是任务清单，做完一条划掉一条。标“待验证”的判断来自读代码，推进到那一步时先验证再动手。

## 目标与边界

- **独立的终端客户端**，不依赖图形客户端安装或运行。仓库里与图形客户端放在相邻位置，尽量共用代码。
- **Claude Code 的 TUI 原样透传**：显示和按键一比一中继，不改造、不注入按键。增强只放在 TUI 外面，以子命令的形式提供，与图形客户端的项目、会话概念一致。
- **会话与图形客户端打通**：终端里能接续图形客户端的会话；终端里聊的内容，图形客户端的上下文和记录里都要有。
- **用量统计打通**：终端的调用计入同一份统计。
- **身份是交互式 CLI**：终端路线不能被识别成 SDK 调用，见“CLI 与 SDK 的身份边界”。
- **本次不改图形客户端的内嵌原生终端**。等 `ccdt` 可用后再决定是否用它取代内嵌终端。因此服务端的新行为一律由 `ccdt` 显式请求才生效，内嵌终端打开时行为不变。

## 已有的基础

| 需要的能力 | 现状 | 代码 |
| --- | --- | --- |
| 经 WSS 中继终端 | 已有一组终端消息：原始字节、窗口尺寸、按字节确认的流控（128 KB 暂停，32 KB 恢复） | `apps/server/src/native-terminal.ts`、`server.ts` 的 `openTerminal` |
| 设备执行通道 | 连接桥、通道分发、Windows 与 POSIX 的 SSH 服务端都是纯 Node 模块，不依赖 Electron | `apps/desktop/electron/proxy-bridge.mjs` 及其引用的 `.mjs` |
| 同一台电脑多个连接 | 服务端按设备 ID 建席位，一个席位可挂多个连接；执行通道用最后连上的那个，它断开时切回其余的 | `server.ts` 的 `seat`/`vacate` |
| 项目与会话 | 列表、订阅、新建都在现有协议里 | `packages/protocol` |
| 用量统计 | 终端进程已注入遥测变量，请求记录进入同一个统计库 | `server.ts` 设置 `options.claude.environment`，`usage.ts` |

#9 的评估记录里有一条实测约束：Windows 上把打包的 Electron 当 Node 运行时，输入端不是终端，raw 模式用不了（见[评估记录](linux-client-and-tunnel.md#终端客户端)）。独立客户端自带控制台程序形态的 Node 运行时，这个问题不存在。

## 形态与仓库位置

- `apps/cli`：`ccdt` 本体，Node 24，与服务端一样直接运行 TypeScript 源码。
- 连接桥（`apps/desktop/electron/proxy-bridge.mjs` 及其引用的模块）是纯 Node 模块，本来就是给图形端页面中继一条本机 WebSocket。`ccdt` 直接引用它，像页面一样连上去，图形客户端一行不改。原计划把它移到共享包，推迟到定分发形态时再做：那时 `ccdt` 要单独打包，搬迁和打包配置一起改，现在动只会增加图形客户端打包出错的风险。
- 协议版本必须和服务端一致。本分支改了协议（`terminal.open.continueSession`、`terminal.detached`），发版时 `PROTOCOL_VERSION` 要升一版。`ccdt` 连接时检查版本，不一致时提示升级。它和图形客户端各自升级，互不牵连。
- 分发形态（npm 包、自带运行时的压缩包或安装包）留到功能可用后再定。Windows 上还要带 OpenSSH 的 sshd，图形客户端安装包现在是自带的。

## 连接、登录与设备身份

- `ccdt login <地址>`：在终端里输入 Token（不回显），可选保存；也支持 `--token-stdin` 和 `CCDT_TOKEN` 环境变量。服务地址和证书指纹默认取图形客户端保存的值。可以保存多个服务端，与图形客户端的“多个连接”对应。
- **设备身份**：本机装有图形客户端时，读取它的 `settings.json` 里的 `deviceId`，服务端就把两者视为同一台设备；没有装时由 `ccdt` 自己生成并保存。
- **复用图形客户端保存的登录**（待定）：图形客户端用 Electron 的 `safeStorage` 加密 Token。Windows 上可以用 DPAPI 解开，但这依赖 Chromium 的内部存储格式；macOS 上读钥匙串会弹出授权框。推进到这一步时再比较各种做法。
- **两个进程都在线时**（待验证）：两个客户端各自运行一个本机 SSH 服务端，要确认端口和主机密钥不冲突，并且执行通道在两者之间切换时正在执行的命令不受影响。

## 会话连续性

结论：可以做，而且大部分是现成的。有一个前提要先验证；另外有几种情形只能做到“如实提示”，需要确认是否可以接受。

### 上下文：同一个原生会话，天然连续

- 图形客户端的每一轮经 SDK 运行。原生会话 ID 就是本项目的会话 ID：第一次用 `sessionId`，之后用 `resume`。CLI 的会话记录存在 `nativeRoot` 对应的目录下（`server.ts:548`、`claude.ts:184`）。
- 内嵌终端在同一个目录、同一个 HOME 下启动 CLI，但现在没有带会话参数，每次都是一段新会话。
- `ccdt` 打开终端时，服务端改为：会话已有原生上下文就带 `--resume <会话 ID>`，否则带 `--session-id <会话 ID>`。这样终端里的每一轮写进同一份 CLI 会话记录。图形客户端下一轮 `resume` 时读到的就是包含终端对话的完整上下文。上下文不需要额外同步。
- **前提（已验证，见文末“验证记录”）**：交互式 `claude --resume <id>` 在原会话 ID 下续写，不另起 ID；SDK 的 `resume` 和交互式 CLI 可以交替续写同一个会话。
- 终端第一次建立原生会话时，服务端要补记一个 `native.session` 事件。`hasNativeContext` 靠这个事件判断，否则图形客户端下一轮不会 `resume`。

### 记录：每一轮结束时，把新增的对话导入图形客户端

- 图形客户端显示的是本项目自己的事件记录，由 `ClaudeStream` 把 SDK 消息转换而来。终端里的对话不经过它。
- 做法：
  1. 服务端打开终端时，用 SDK 的 `getSessionMessages` 记下原生会话最后一条消息。
  2. 终端里每一轮结束时，以及终端结束时，再读一次，取出还没导入的消息。
  3. 把这些消息交给同一个 `ClaudeStream` 转换成事件，标明来自终端。
- 好处：
  - 只有一条转换路径，图形客户端看到的终端对话和自己运行的对话格式相同。
  - 读取用的是 SDK 的公开接口，不自己解析会话文件。
  - 工作都在服务端，`ccdt` 和以后的内嵌终端都适用。
- 导入的内容不如实时运行完整：没有流式过程，也没有审批记录，终端里本地命令的输出（例如 `/usage` 面板）也看不到。导入的只有消息正文、工具调用和结果。
- 实现：`apps/server/src/terminal-transcript.ts`。打开时记下原生会话已有的全部消息 ID，结束时导入其余的。压缩会在摘要之后保留一部分旧消息，按 ID 排除后不会重复显示。压缩摘要由 `isCompactSummary` 识别，记成一次压缩；CLI 自己写的说明（`is_meta`）和不是使用者输入的消息（`origin.kind` 不是 `human`）不导入；本地命令显示为命令本身和它的输出。这些字段 `getSessionMessages` 都会带上，2026-11-01 用 CLI 2.1.293 实测过。
- 会话切换由 SessionStart hook 记录：终端用一份自己的设置文件，内容是服务的提供方设置加上这个 hook，`--settings` 改为指向它。这个文件和 hook 写入的记录放在数据目录的 `terminals/` 下，权限 0600，终端结束时删除，服务启动时整个目录清空。
- 时机：每一轮结束时（CLI 的 Stop hook）导入这一轮，终端结束时再导入剩下的。一轮进行中的流式过程不实时显示：CLI 的记录在一轮结束前不完整，逐条跟着读收益不大。

### 只能如实提示的情形（需要确认是否接受）

| 终端里的操作 | 后果 | 打算的处理 |
| --- | --- | --- |
| `/clear`、`/resume` 到别的会话、新开会话 | CLI 换了原生会话，之后的对话不在这个会话里 | 只导入切换之前的部分，并记一条提示。切换由 CLI 的 SessionStart hook 发现：`/clear`、`/resume` 之后它报告新的 `session_id`（jiangan-code 分支的做法：hooks 写进原生目录的 `.claude/settings.local.json`，保留使用者自己加的 hooks） |
| 回退（`/rewind`、双击 Esc） | 原生会话从某处分叉，图形客户端已显示的部分内容不再在上下文里 | 记下的最后一条消息不在当前链上时，记一条“终端中回退了对话”的提示，再从分叉点导入。事件记录只追加，旧内容保留 |
| `/compact` | 上下文压缩 | 读取时带上系统消息，转换成已有的压缩事件 |

同一个会话不能同时在图形客户端和终端里运行，现有的“忙碌”锁已经保证了这一点。来回切换的意思是：一边结束，另一边接续。

## 终端的生命周期：和本地的 claude 一样

本地的 `claude` 窗口开着就一直运行，关掉窗口就结束。`ccdt` 照此：窗口就是 claude。还有一点约束：`ccdt` 进程同时是 Claude 回到这台电脑执行命令的通道，窗口关了，服务端的 Claude 也执行不了命令了，所以没有“关窗口后留在后台”这种用法，也不占任何快捷键，所有按键原样交给 Claude Code。

- **窗口开着**：连接一直保持，两端都有心跳。断网时 `ccdt` 自动重连，服务端在宽限期内（与运行相同，`PROXY_GRACE_SECONDS`，默认 5 分钟）保留终端，连回来后先画出当前整屏再接着显示。无人值守的长任务就是窗口一直开着。
- **关窗口**（Windows 关闭控制台、POSIX 的 SIGHUP/SIGTERM）：`ccdt` 先请求结束它显示的终端（`terminal.close`），再断开。它不告诉服务端“主动离开”（`leave`）：`ccdt` 是这台电脑最后一个连接时，那会让服务端立即结束这台电脑留在服务端的一切，例如图形客户端断线后还在宽限期里的运行、另一个断了线的 `ccdt` 窗口的终端。进程被强行结束、来不及请求的，按断线处理，宽限期过后结束。
- **退出 Claude Code**（`/exit`）：终端结束，`ccdt` 跟着退出。
- 同一个会话在第二个窗口里打开：接过显示，原来的窗口收到 `terminal.detached`（`taken`），提示后退出。客户端 30 秒不确认输出（`stalled`）时也停止向它发送，它随即重新打开，接着显示。

整屏重画采纳 jiangan-code 分支的做法：服务端给每个终端维护一份屏幕状态（`@xterm/headless` 加 serialize 插件），重新接入时先发当前整屏，再接实时输出，同时恢复键盘模式（kitty 键盘协议、modifyOtherKeys）、鼠标编码和光标显示。这些只对 `ccdt` 打开的终端生效，内嵌终端不变。

`ccdt` 本地还做到：退出或断线时恢复本机终端的状态（光标、括号粘贴、鼠标与焦点上报、备用屏幕）。

### 终端开着时，另一边看到什么

同一个会话同一时间只能在一处使用，服务端本来就互斥（终端占着会话，图形客户端发消息会被拒绝；图形客户端在运行时，终端打不开）。只靠拒绝，使用者要发出去才知道，所以两边事先显示：

- 终端的 CLI 用 hooks 报告它在做什么，写进终端自己的 hooks 文件，服务端边写边读（每 0.5 秒查一次）。状态记在 `run.status.activity`，会话摘要的 `activeRun.activity` 同步：
  - 运行中：`UserPromptSubmit`，以及工具跑完的 `PostToolUse`、`PostToolUseFailure`（确认过了，接着运行）。
  - 等你确认：`PermissionRequest`。CLI 2.1.293 弹出确认时只运行它，不发 `Notification`（`permission_prompt`），后者仍按“等你”处理，以防别的版本发。
  - 空闲：`Stop`、`SessionStart`，以及 `Notification` 的 `idle_prompt`。
  - 中断：使用者按 Esc 或 Ctrl+C 中断一轮时，CLI 不运行任何 hook，记录里也不留痕迹（实测：被中断的提示之后直接是下一条提示，没有 `turn_duration`，也没有“interrupted”字样；`idle_prompt` 等了 80 秒也没有来）。所以服务端在“运行中”时看终端输入：单独的 Esc 或 Ctrl+C（含 kitty 键盘协议的写法）之后 2 秒内没有新的 hook，就当作这一轮已中断，回到空闲并导入。
  - CLI 自己报告：2.1.295 起 CLI 支持 OSC 7501（Program Status Protocol）。它启动时问终端支不支持，得到回答后每次状态变化输出一段 `state=working|blocked|done|idle|error`。服务端替终端回答这个问题（问题本身不转给客户端的终端），读主对话的报告：`working` 为运行中，`blocked`（等审批或提问）为等你确认，其余为空闲；中断一轮时 CLI 立即报告 `idle`，不用再等上面的推断。报告照常转给客户端的终端，支持它的终端也能显示。2026-11-10 用 CLI 2.1.321 在伪终端里对着本地模拟接口实测：启动 `idle`，提交后 `working`，按 Esc 后 `idle`，一轮结束 `done`。Windows 的 ConPTY 会抢先回答同一批里的设备属性查询，CLI 便认为终端不支持；服务端在 Linux 的真实 pty 里没有这个问题，Windows 上的实测改用 node-pty 自带的 conpty.dll。
- 图形客户端：会话列表和对话底部显示“终端运行中”“终端等你确认”“终端打开中”，输入框变灰并提示关掉终端后可以接着聊，停止按钮不显示（终端的运行由终端自己中断）。
- `ccdt`：`sessions` 与 `-r` 标出谁在用这个会话；会话正在图形客户端里运行，或开着图形客户端的内嵌终端时，不去打开，直接说明原因。另一个 `ccdt` 窗口开着的照旧接过来。

## 外壳的易用性

内层是原版 Claude Code，不改。`ccdt` 自己这层：

- 用法对齐 `claude`：`ccdt` 接着当前项目最近的会话（像 `claude -c`），`ccdt -r` 用方向键选（像 `claude -r`），`ccdt new` 新开。不需要接触会话 ID；`ccdt open <ID>` 只留给脚本。
- 服务端为项目建的工作目录名是随机 ID，Claude Code 界面里显示的就是它；目录不能改名，否则 CLI 找不到已有的会话记录。所以 `ccdt` 进入之前先显示一行“项目 … 会话 …”。
- `ccdt login` 不写地址时，用图形客户端保存的服务地址和证书指纹，只需输入凭据。
- 连接时显示“正在连接 …”，断线时显示“正在重连”，退出时说明怎样接着聊。
- `CCDT_LOG=<文件>` 记录连接过程，用于排查连不上或断线。

## 用量统计

- 终端进程已经带上了遥测变量。改用 `--resume`/`--session-id` 之后，CLI 上报的会话 ID 就是本项目的会话 ID，统计按会话归属自动对上（待验证）。
- `ccdt usage` 复用现有的统计查询消息。
- 测试只覆盖会话归属这一项。

## CLI 与 SDK 的身份边界

社区报告经 SDK 和 `-p` 调用时 5 小时额度消耗更快（官方未确认）。SDK 识别自己用的是子进程环境里的 `CLAUDE_CODE_ENTRYPOINT=sdk-ts`，它只写在传给子进程的环境副本里（SDK 0.3.286），不会改变服务进程自己的环境。终端路线遵守以下几条，并在代码里写明原因：

- 只在伪终端里以交互方式启动官方 `claude`。不经过 SDK 的 `query()`，不用 `-p`、`--output-format`、`--input-format`。
- 启动环境主动去掉 `CLAUDE_CODE_ENTRYPOINT` 和 `CLAUDE_AGENT_SDK_*`，防止从别处继承进来。
- 只用普通的交互式参数：`--resume`/`--session-id`、`--model`、`--effort`、`--settings`、`--permission-mode`、`--append-system-prompt`。
- 不用程序按键驱动 TUI。
- 一个单元测试检查最终的环境和参数。开发实测时抓一次请求头对比 User-Agent，确认终端是 `cli`、图形客户端是 `sdk-ts`。

图形客户端那条路仍然经过 SDK，这一点不变。

## 不采纳的部分

jiangan-code 分支里另有这些，不进本方案：终端里的 agent 列表、worktree、Herdr 集成、本机后台服务（daemon）、按线路选择的 SSH 转发（`ccdt-tunnel`）；断线恢复后自动提交一条提示让 Claude 继续（违背不注入输入）；多个 Claude 账号轮换与 Codex 账号池（与[路线图](../roadmap.md#明确不做)对订阅用法的约束相冲突）。

## 推进时再定的事项

- 终端第一次在一个项目里打开时，Claude Code 会问是否信任它的工作目录（`/data/state/native/<项目>`），默认选项是“No, exit”。这是 Claude Code 自己的对话框，暂时不动，等有体验和反馈再定（2026-11-01 决定）。

- `ccdt` 可用后，内嵌原生终端是否由它取代。

已定下的：

- 登录：装有图形客户端时，服务地址和证书指纹取自它保存的设置，只需输入服务凭据；设备 ID 与它共用。Token 存进各系统的密钥服务（DPAPI、钥匙串、Secret Service），用不了时存进只有本账号可读的设置文件。
- 分发与升级：每个系统一个自带 Node 的压缩包（Linux 有 x64 与 arm64），附安装脚本，随发版放在同一个发布页；升级是下载新版本再运行一次安装脚本。版本与服务端不一致时，服务端拒绝登录，`ccdt` 给出对应版本的下载页。

## 验证记录

### 2026-11-01：会话 ID 与请求身份

在测试机的临时容器（`node:24`）里，用 CLI 2.1.293 和 SDK 0.3.286，对着一个本地模拟的 Messages 接口运行，不消耗真实额度。交互式 CLI 由伪终端驱动，和服务端的原生终端一样。

| 步骤 | 结果 |
| --- | --- |
| 交互式 `--session-id S` 聊一轮 | 会话记录 `S.jsonl` |
| 交互式 `--resume S` 再聊一轮 | 仍写入 `S.jsonl`，没有新文件 |
| SDK `query({ resume: S })` 一轮 | 初始化和结果都报告会话 `S`，写入 `S.jsonl` |
| 交互式 `--resume S` 聊一轮，`/clear`，再聊一轮 | `/clear` 之前的一轮写入 `S.jsonl`；之后的写入新会话，退出时提示的接续 ID 也是新的 |
| `getSessionMessages(S)` | 依次是前四轮的问与答，SDK 那一轮夹在中间，顺序正确 |
| SessionStart hook | 依次报告 `startup`、`resume`、`resume`、`clear`，`clear` 带着新会话的 ID |
| 请求头 User-Agent | 交互式为 `claude-cli/2.1.293 (external, cli)`；SDK 为 `claude-cli/2.1.293 (external, sdk-ts, agent-sdk/0.3.286)`。两者的 `x-app` 都是 `cli` |

结论：会话连续性的前提成立；`/clear` 的切换能由 hook 准确发现；交互式终端的请求身份是 `cli`，与 SDK 可以区分。测试容器和拉取的镜像已删除。

### 2026-11-01：Linux 客户端（第四次端到端，同一台 devbox 既是服务端也是客户端）

服务端照常部署在 devbox 的容器里；`ccdt` 用 GitHub 打出的 Linux x64 包，装进一个临时的 HOME，在经 SSH 登录、没有图形界面的会话里，由 Python 的伪终端驱动：

- 登录：放一个连不上桌面会话的 `secret-tool` 在 PATH 前面，凭据存进权限 600 的设置文件，并提示了这一点。此前这种情况下 `ccdt login` 会直接失败，已修。
- 执行通道：模拟的模型按系统提示词的写法发 `ssh -F … device-script` 运行 `hostname; pwd`，输出是 devbox 的主机名和 HOME，命令确实回到了客户端这台机器上运行。
- 终端状态与逐轮导入：运行中 → 等你确认（`PermissionRequest`）→ 确认后结束，回到空闲并同时导入这一轮。两个 hook 落在同一次读取里时只记最后的状态。
- 服务端暂停 50 秒：`ccdt` 显示正在重连，恢复后接回原来的屏幕，接着聊。
- 关窗口（对伪终端发 SIGHUP 并关掉它）：`ccdt` 以 129 退出，服务端同一秒记录终端结束。此前写入已关闭的终端会出错，`ccdt` 以 1 退出，已改为按关窗口处理。
- 会话属于另一台不在线的电脑时（删掉设置后重新登录就会这样），`ccdt` 说明原因并在 2 秒内退出。此前它会一直挂着，已修。
- `ccdt sessions`、`ccdt -r` 正常；中文目录名正常。

### 2026-11-01：真实模型与整体复查（第五次端到端）

服务端部署在 devbox，模型换成 DeepSeek 官方接口的 `deepseek-flash`；`ccdt` 用打好的 Windows 包在伪终端里操作，另开一个连接记录服务端推送的内容：

- 执行通道：Claude 新建并运行 `hello.ps1`，经 `ssh … device-script` 把脚本发回这台 Windows 运行，手动审批下先弹确认，确认后输出正确、退出码 0。
- 上下文连续：终端一轮 → 图形客户端一轮 → `ccdt -r` 接回，两边各自记得对方那一轮说了什么。
- 图形客户端运行中时 `ccdt` 不打开该会话，列表有标记；关窗口后会话不再被占用；`ccdt usage` 对第三方接口如实说明没有订阅额度。

复查中修掉的问题：

- `ccdt` 退出时发 `leave`：它是这台电脑最后一个连接时会让出座位，连带结束服务端为这台电脑保留着的东西（比如等客户端回来的图形客户端运行）。现在只关连接，交给服务端按断线处理。
- 终端什么都没说就退出时，`--session-id` 留下一个空的原生会话，之后图形客户端和终端用这个 ID 都会被 CLI 以“已在使用”拒绝。现在退出时、以及打开前发现残留时都删掉它。
- 记录终端状态时挪动了这一轮事件的时间下限，一轮里的工具耗时显示为 0.0 秒。现在状态记录不影响事件时间，命令耗时如实显示。
- 会话列表的条目超过终端宽度时折行，重画时位置错开。现在按终端宽度截断（中文按两格算）。
