# 历史读取性能与传输边界

2026-11-15，针对 #188 提出的历史读取超时和状态查询冲突，先在服务端修复读取职责及查询成本。此次只改 `store.ts`、`server.ts` 两个实现文件，不修改客户端、协议、表结构或部署配置。

## 取舍与实现

原分页查询先对游标之前的事件正文按轮次汇总大小，再选最近一页；后面的 `LIMIT` 并不能避免前面的全量聚合。现在先通过已有的 `events_run(session_id, run_id, sequence)` 覆盖索引寻找轮次，再用复用的预编译查询，只统计填满一页所需的轮次。没有增加索引、缓存或迁移。索引读取仍随历史规模增长，不宣称常数时间。

SQLite 的 `length(TEXT)` 计算字符，原先却把它当作字节预算。分页与断线补读均改用 `octet_length(data)` 统计 UTF-8 字节。中文页可能包含更少轮次，但记录仍能继续向前读取。1000 事件 / 512 KiB 仍是软预算，单个超大轮次完整保留；没有截断输出、丢弃记录或限制可读历史长度。

原生状态查询不会修改已有历史，却与删除、改名、分叉共用同一个会话锁，导致订阅和翻页也被拒绝。锁现在记录持有原因，只有状态查询期间允许 `session.subscribe` / `session.history`；其他操作以及会话变更期间的互斥不变。这样无需各客户端自行排队，也覆盖另一窗口的读取。

功能核对以全部历史内容、序号、游标、重连和变更互斥等效为准，不要求错误字节预算下的页边界保持不变。没有性能与内容完整性之间的产品取舍。

## 验证方法

基线为 main 的 `da2a7c7`。使用实际 `SessionStore.history()` 对比原版、仅修字节计数的参考版和最终实现，未用独立 SQL 探针代替产品代码。样本包括随机轮次 ID 的一万轮记录、早期大输出而近期小输出、中文、单个约 6 MB 轮次、状态事件穿插与序号间隙。

每项预热两次，测五次取中位数。计时包括分页和所选事件解析，不包括网络及绘制。逐页比较全部字段，并核对拼接结果等于完整历史；所有样本的新实现与按字节计数的参考版一致，ASCII 样本还与原版逐页一致。一万轮样本遍历 94 页、30000 个事件。重连另比较零游标、早期游标、中间游标和末尾游标。

锁竞争使用真实服务端与两个 WebSocket 客户端，只将原生状态查询和 SDK 会话变更替换为受控等待，以排除真实账号和外部网络。对照确认：

- 原版在状态查询期间，同窗口和另一窗口的订阅、翻页均返回 `session_busy`；新实现立即完成读取，状态查询结束后的新事件仍送达订阅者。
- 状态查询期间移动会话、移动项目仍被拒绝；改名、分叉、删除进行中仍拒绝订阅和翻页；这些操作完成后结果正常，已删除会话不能再订阅。
- 仓库历史回归覆盖旧库合并后的序号间隙、小差量补读和非法游标；新增三个用例覆盖多字节预算与全量还原、超大单轮及其前页、1000 事件上限。

Windows（Node 24.21）完整回归：379 项通过，35 项按既有条件跳过，无失败。Linux（Node 24.22，隔离容器限制 1 CPU / 1 GiB）历史、服务端及浏览器接入的 52 项相关回归全部通过，锁竞争与逐页内容对照也通过。类型、格式检查通过。Linux 测试所需的编译依赖只安装在临时容器内，未修改宿主环境。

| 实际 history() 样本 | Windows 原版 → 优化后 | Linux 原版 → 优化后 |
| --- | ---: | ---: |
| 一万轮 | 209.85 → 7.31 ms | 87.70 → 5.65 ms |
| 早期大输出、近期小输出 | 248.42 → 3.12 ms | 115.28 → 3.25 ms |
| 中文 | 19.98 → 1.55 ms | 13.56 → 1.90 ms |
| 最后一轮约 6 MB | 43.23 → 5.81 ms | 34.43 → 8.68 ms |
| 状态事件穿插与序号间隙 | 7.08 → 1.89 ms | 4.31 → 1.88 ms |

中文页由 1,445,223 字节变成 482,091 字节；这个样本的耗时收益同时包含少读记录和查询方式改进。其余样本的返回页内容、体积均与原版一致。这些是合成数据的预热后比较，不是生产平均耗时。

## 优化后还剩什么

使用实际服务端、TLS/WSS、桌面连接桥和未修改的 `ProxyClient`，在 TCP 下行限速下比较：

| Windows 样本 | 原版 | 服务端优化后 |
| --- | --- | --- |
| 中文历史，96 KiB/s 下行上限 | 历史约 10 秒超时，随后用量查询也超时 | 历史约 5.4 秒加载完成，用量响应随之到达 |
| 单轮约 6 MB，512 KiB/s 下行上限 | 历史约 10 秒、用量查询约第 11 秒超时 | 同样超时 |

Linux 容器内运行同一套真实服务端、连接桥与客户端探针，中文页约 5.0 秒完成；6 MB 单轮的两类超时同样复现。

第二行没有因为 SQL 变快而消失。第一行的用量响应也要等历史传完，说明当前仍存在消息排队。限速值是设定上限，不是保证的实测吞吐；没有用合成样本推断线上发生率，也没有真实 Claude 账号验证。

建议下一步优先处理历史传输的有界性，而不是继续强化 SQL、迁移数据库或只延长客户端超时。先验证有限的历史应用消息分块，服务端按块发送并限制排队，普通响应可在块间通过；若这需要复杂调度器，则比较独立 HTTP 历史读取。客户端只增加与所选传输契约直接相关的组装、进度和取消处理。

底层 WebSocket 分帧只保证控制帧可以穿插，不意味着普通用量响应也能插进尚未完成的历史消息，见 [RFC 6455 §5.4](https://www.rfc-editor.org/rfc/rfc6455#section-5.4)。独立 HTTP 方案也要处理实时订阅与快照交界的事件顺序，并复用现有认证、证书与代理要求，不能只加一个下载请求。

标准压缩在前期探针中对公开源码、模拟日志有明显减量效果，但没有解除队列阻塞；其端到端 CPU、内存和并发成本尚未验证，适合作为后续补充。纯状态页自动续读等客户端交互可以另作小改动，不是大消息阻塞的解法。

本次可独立交付，但不能将 #188 的全部问题标为已解决。下一阶段应围绕已复现的大历史阻塞，验证控制操作、切换、取消、重连与桌面/浏览器一致性；不借此重写同步引擎，也暂不扩大到尚无实测瓶颈的渲染与存储架构。
